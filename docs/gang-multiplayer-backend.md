# GANG MODE — Secure Multiplayer Backend Contract

Status: production contract for the NOCTURNE / GANG MODE room transport.

The game rules and round state machine remain owned by `packages/gang-core`. The database is transport and persistence, never a second game engine.

## Architecture

- **ONE PHONE** uses the core runtime locally and needs no room backend.
- **EVERYONE IN** uses a six-character room code plus a per-client bearer capability.
- **BIG SCREEN** joins the same room as a display-only client and never consumes a player seat.
- The elected **facilitator** is the oldest active input player. Display-only clients can never become facilitator.
- Public room state contains only presentation-safe data. The complete canonical runtime is stored in the private server schema for failover.
- Private roles/missions are generated by the canonical core runtime and synchronized to the database. The database does not independently randomize game roles.

## Security invariants

1. Player tokens are random 24-byte values and are stored server-side only as SHA-256 hashes.
2. Player tokens never belong in URLs, QR codes, public room state, analytics or visible UI.
3. The room code may be shared and embedded in join/screen URLs.
4. The `gang` schema is private:
   - no `USAGE` for `anon` or `authenticated`;
   - no direct table grants to browser roles.
5. Browser access is limited to named `SECURITY DEFINER` RPCs with an empty pinned `search_path`.
6. A player can read only their own pre-reveal private payload.
7. Only the current facilitator can:
   - mutate room stage/public state,
   - collect a completed stage's actions,
   - synchronize core-generated private payloads,
   - persist/load the complete core runtime,
   - read raw reveal mappings after the reveal gate.
8. Display-only records have `can_input=false`; they do not count toward `max_players` and are excluded from facilitator election.
9. Room state writes use optimistic `version` checks. Clients must refetch on `version_conflict`; they must not force overwrite.
10. Rooms expire after 12 hours. Room creation opportunistically deletes expired rooms and cascades their player/action/private data.

## RPC surface

The canonical TypeScript names live in `packages/gang-core/src/transport.ts`.

- `gang_create_room`
- `gang_join_room`
- `gang_join_display`
- `gang_room_snapshot`
- `gang_leave_room`
- `gang_set_room_state`
- `gang_submit_action`
- `gang_collect_stage_actions`
- `gang_stage_progress`
- `gang_get_private`
- `gang_set_private_payloads`
- `gang_reveal_round_data`
- `gang_save_runtime`
- `gang_load_runtime`

There is deliberately **no database-side private-role randomizer**. Undercover, One of You, Secret Missions, Draw This, Bluff and similar private payloads come from the core runtime and are synchronized by the facilitator.

## Client lifecycle

### Create / lobby
1. Host creates a room and receives `playerToken + snapshot`.
2. Store the token session-scoped.
3. Share only the room code or `/gang?join=CODE`.
4. Poll snapshots modestly and refresh immediately after local actions.
5. Start only when active input players satisfy the selected game/queue ranges.

### Start / stage
1. Facilitator builds the canonical runtime using active input player IDs/names.
2. Persist it with `gang_save_runtime`.
3. Publish the safe `publicGangView` through `gang_set_room_state`.
4. If the round has private payloads, map `privateGangView` for each player and sync them with `gang_set_private_payloads`.
5. Each controller submits one stage action.
6. When progress is complete, facilitator collects actions and feeds them into `submitGangAction` in the core runtime.
7. Advance the runtime, persist it and publish the next safe public state.

### Reveal
- Controllers never receive another player's private payload before reveal.
- Facilitator may use `gang_reveal_round_data` only after the room reaches reveal/score/finished.
- Anonymous answer voting stays anonymous in presentation until reveal.

### Failover
- Snapshot/leave operations re-elect only active input players.
- A newly elected facilitator calls `gang_load_runtime` and continues the same canonical session.
- Big Screen may remain connected throughout and never acquires facilitator authority.

## Scale / cost

The room backend uses the existing Supabase/Postgres project; no additional paid provider is required.
Polling should default to roughly 750–1000 ms while visible and should slow/pause when the document is hidden where safe.
Big Screen should render aggregate progress for large rooms rather than 99 individual controls.

## Verification already performed

Backend integration checks cover:
- four-player Undercover private payload delivery and vote/reveal flow;
- 30 distinct Secret Missions for 30 players;
- two controllers plus a display-only client;
- display device not consuming the room's player limit;
- display device never becoming facilitator;
- facilitator failover with persisted runtime recovery;
- zero direct browser grants to the private `gang` schema.
